Creational pattern

Factory Method

A creator provides a method for making a product. Different creator classes choose which concrete product is returned.

Main thought: “Which object should this workflow use?”

Factory Method is useful when a workflow is common but the product used by that workflow can vary. The client works with a product interface instead of constructing a specific product itself.

Delivery company analogy: the delivery plan stays the same. A road office sends a truck; a sea office sends a ship. Each office decides which vehicle it provides.

Object creation flow

Client chooses creator
→
Workflow calls factory method
→
Creator makes concrete product
→
Workflow uses product interface

Why this name? The factory method is the creation point. Creator implementations provide the concrete product while reusable code handles the rest of the workflow.

The problem it solves

Without a creation method, every caller may need a growing if/else or switch to construct concrete classes. Factory Method moves that decision to a creator implementation, keeping the workflow independent of product classes.

Think of it when several related products share an interface and you want different creator types to choose the product for a reusable workflow. For one simple product, a direct constructor may be easier.

Java and Spring connection

A Spring @Bean method creates and returns an object for the Spring container. It is a useful method-based creation example, though Spring bean management is broader than the GoF pattern.
