Two minute mental model

Lead with this; expand based on the interviewer’s follow-up.

A sealed type controls its direct inheritance edges. The declaration names which classes or interfaces may directly extend or implement it. Every permitted child continues the policy as final, sealed, or non-sealed. A sealed hierarchy is closed at its root, but a non-sealed permitted branch is open below that point.

The payoff is a modeled finite set of alternatives. In Java 21+, pattern matching for switch can use that hierarchy for exhaustiveness checks. The cost is ownership of the subtype set and tighter evolution coupling between producers and consumers.

Interview opener: “I use sealed types when the domain has a deliberately bounded set of variants that I own—such as command outcomes or an expression AST. They make the boundary explicit and enable exhaustive handling, especially with records and Java 21 pattern switch. I avoid them when third-party extension is a core requirement.”

Modifier on permitted direct child Meaning Inheritance after that child
final Closes the branch No subclasses
sealed Continues controlled admission Only its permitted children
non-sealed Explicitly reopens the branch Ordinary unrestricted subclassing

Senior design lens

At 10 years’ experience, trade-offs and migration thinking matter as much as syntax.

Model boundaries

Choose a sealed interface when…

You want unrelated implementations to share a capability while keeping the set of direct implementations under your control. For example, sealed interface PaymentResult permits Authorized, Declined, Retryable. Variants can be records, enums, or classes.

Choose an abstract sealed class if variants should share state, constructors, protected helpers, or common implementation. Java still allows one class superclass, while interfaces permit multiple inheritance of type.

Change management

Closed-world modeling is an API promise.

Adding a permitted subtype can require recompiling exhaustive switches. With separately compiled Java 21 consumers, a consumer built against the old hierarchy can fail at runtime with MatchException if the new subtype reaches an old exhaustive switch. Treat additions as a compatibility and rollout concern: coordinate versions, recompile downstreams, or provide an intentional fallback where forward compatibility matters.

Adding default trades compiler pressure to handle new variants for runtime fallback behavior. It can hide missed business handling, so make it intentional and observable.

Domain modeling

Sealed vs enum vs open interface

Use enum for fixed singleton constants with the same shape. Use a sealed hierarchy when alternatives carry different data or behavior, need distinct types, or form multiple controlled levels. Use an open interface when third-party extension is central.

A sealed hierarchy is not a complete algebraic data type facility: nulls, generic variance, serialization, mutation, and evolution still need deliberate design.

Production boundary

Where are permitted types restricted?

For a named module, the sealed type and its permitted direct subclasses/subinterfaces belong to the same module, but can be in different packages. In the unnamed module, they must be in the same package.

Consider module ownership, package layout, and source organization before sealing a public API.

Code and debugging drills

Predict the result before opening the explanation.

Drill 01 · classify

Which declarations compile?

sealed interface Event permits Created, Updated {} record Created(String id) implements Event {} non-sealed class Updated implements Event {} class Patched extends Updated {} class Deleted implements Event {}

Created compiles and is implicitly final. Updated declares non-sealed; Patched may extend it. Deleted fails because it is not permitted by Event.

Drill 02 · inferred permits

Can permits be omitted?

sealed interface Outcome {} final class Ok implements Outcome {} final class Error implements Outcome {}

Yes, when permitted direct types are declared in the same compilation unit. The compiler infers Ok and Error. When variants are in separate source files, list them in permits.

Drill 03 · switch coverage

Is this Java 21 switch exhaustive?

sealed interface Reply permits Success, Failure {} record Success(String value) implements Reply {} record Failure(String reason) implements Reply {} static String message(Reply r) { return switch (r) { case Success s -> s.value(); case Failure f -> f.reason(); }; }

Yes. It covers both permitted variants; records are final. Java 21 pattern-switch syntax is final. A null selector still throws NullPointerException unless case null is present.

Drill 04 · runtime evolution

Old consumer, newly permitted subtype

// Old consumer compiled for Success, Failure: return switch (reply) { case Success s -> "ok"; case Failure f -> "failed"; }; // Library later adds Retryable to Reply

Recompile the consumer. If the new subtype reaches stale exhaustive-switch bytecode, Java 21+ throws MatchException. Exhaustiveness is reasoned about at compile time; independently deployed binaries can drift.

Design exercise · 5 minutes

Model a payment processing result

Model authorized (authorization id + amount), declined (reason + retryability), and pending (provider reference). Discuss whether retryable decline is a separate variant, API ownership, serialization versioning, and whether behavior belongs in variants or a Java 21 switch. Strong answers use variants that reflect meaningful domain distinctions, validate invariants at construction, and seal only when the owning module really owns the full variant set.
