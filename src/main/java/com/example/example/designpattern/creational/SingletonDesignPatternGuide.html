Creational pattern

Singleton

Singleton gives callers one shared instance through a controlled access point. These examples compare common ways to create or retrieve it.

Main thought: “Do callers need one shared instance?”

The class prevents callers from constructing independent copies and provides a method or constant that returns the shared object.

Simple analogy: one Prime Minister at a time. People refer to the same office holder during that term instead of creating a new office holder for every request. In a program, the exact scope of “one” depends on the class loader or container.

Object access flow

Caller asks for instance
→
Class returns saved instance
→
Callers share the same object

Problem it solves: avoids separate instances when an application component is intended to be shared. Common candidates include a registry or configuration holder, though dependency injection is often a better way to manage application services.

Six implementation styles

1. Eager initialization

A static field creates the object as the class initializes. Simple and thread-safe; it creates the object even if no caller asks for it.

Open Singleton01EagerDemo.java

2. Static initialization block

The class initialization block assigns the instance once. Calling getInstance() repeatedly does not run the block again.

Open Singleton02StaticBlockInitialization.java

3. Synchronized lazy initialization

The first call creates the instance. Synchronization protects creation if multiple threads call at once, but every call takes the method lock.

Open Singleton03SynchronizedLazyInitialization.java

4. Double-checked locking

Checks the instance before and inside a synchronized block, with a volatile field. This avoids locking after initialization but is more complex.

Open Singleton04DoubleCheckedLocking.java

5. Initialization-on-demand holder

A nested holder class initializes only when first used. JVM class initialization makes this style lazy and thread-safe.

Open Singleton02HolderDemo.java

6. Enum singleton

The enum constant itself is the shared object. Java also preserves enum identity during serialization.

Open Singleton03EnumDemo.java

Java and Spring connection

Spring beans use singleton scope by default: one instance per bean definition in a Spring application context. This is managed by the container; it is not exactly the classic GoF Singleton, where the class controls its own instance and access point. A Spring @Service is normally injected instead of manually accessed through getInstance(). Keep singleton services stateless or avoid storing request-specific data in fields.

Read more: Spring bean scopes documentation.

Interview one-liner

Singleton restricts a class to one instance and provides a shared access point to it.
